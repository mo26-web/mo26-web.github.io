Causal RCA: Finding Which Sensor Actually Caused the Fault

Try the live demo → View on GitHub

A plant upset almost never announces itself in one signal. A valve sticks, and within minutes the flow wobbles, the level drifts, the temperature follows, and the composition downstream goes off spec. By the time the alarms land, a dozen sensors are all deviating at once and all correlating beautifully with each other.

Correlation cannot tell you which one moved first. That is not a limitation of the particular statistic you chose; it is the definition of correlation. It is symmetric. It has no arrow. Ask it which of two coupled signals caused the other and it will answer both, equally, forever.

Causal RCA is a point-and-click toolbox I built to supply the arrow. It takes multivariate process data, infers a directed, time-lagged causal graph among the variables, and then uses that graph to answer the question a maintenance engineer actually has:

  • Which variable originated this? — root-cause identification.
  • How did it spread from there? — propagation path.

It is the companion to my FDI Analytics Toolbox. That tool answers "is there a fault, and which sensors are affected?" This one answers the next question, the harder one: "which sensor caused it, and how did it travel?" Everything runs in a browser, no coding required. It is live on Azure now, with the manual, quick-start guide, and video walkthrough on GitHub.

The six-stage workflow

You work top to bottom through six stages, and each stage's output feeds the next.

Stages 1 to 3 build the causal graph. Stage 4 watches it change over time. Stage 5 reads the root cause off it. Stage 6 checks whether any of it should be believed.

That last stage deserves a word up front, because it is where causal discovery differs sharply from ordinary machine learning. In supervised learning you hold out a test set and get a number. In causal discovery on real plant data there is no answer key at all: nobody labelled which sensor truly caused the 2023 upset. A tool that hands you a confident graph and no way to interrogate it is asking for trust it has not earned. So validation is a full stage here, not a footnote.

Features, stage by stage

01

Data and scenario

Drag in a CSV or Excel file, inspect each signal, and mark two windows: a stretch of normal operation and the fault period you want explained. If you just want to see how the tool behaves, a built-in synthetic process loads with one click, complete with a known ground-truth graph, so you can watch the methods succeed and fail against a structure you already know.

02

Pre-processing

Causal discovery is far more sensitive to preparation than detection is. Most methods assume stationarity, and a trending signal will manufacture links that are not there.

Steps: stationarity treatment · detrending · differencing · smoothing · scaling · maximum-lag selection.

The maximum lag matters more than any other single setting. Set it too short and you miss slow couplings entirely; too long and you drown the estimator in parameters.

03

Causal discovery

Nineteen algorithms across four families, all sharing one interface and one output format so you can swap between them freely.

Classic and statistical: conditional Granger (VAR), pairwise Granger, lagged cross-correlation, transfer entropy, PCMCI.
Machine learning, traditional: Random-Forest Granger, Gradient-Boosting Granger, SVR Granger, Lasso-Granger, lagged mutual information, VarLiNGAM.
Machine learning, deep learning: Neural Granger cMLP, cLSTM, cGRU, convolutional TCN Granger, temporal attention (TCDF).
Probabilistic: bootstrap edge probability, stability selection, Bayesian regression posterior.

The probabilistic family is worth singling out. Its methods do not return a link or no link; every edge carries a probability and an uncertainty band, and links the data cannot pin down are drawn dashed and dimmed rather than quietly presented as fact. A graph that admits what it does not know is more useful than one that does not.

My standing advice is to run three or four methods from different families and trust what they agree on. Methods resting on different assumptions rarely make the same mistake, and the report's comparison table exists for exactly this.

04

Structural monitoring

The graph is re-estimated on sliding windows across the record, and edges are tracked as they appear, vanish, or drift in strength.

This catches something detection alone cannot. A signal can stay perfectly within its normal range while its relationship to its neighbours changes underneath. A controller quietly saturating, a heat exchanger fouling, a loop retuned last Tuesday: the levels look fine, the structure does not. Stage 4 timestamps that change.

05

Root-cause identification

Candidates are scored on three properties of the graph, with baseline deviation shown alongside as context rather than as evidence:

  • Upstreamness — how near the source of the graph the variable sits.
  • Earliness — how soon its deviation begins relative to the rest.
  • Out-centrality — how much of the network it drives downstream.

The output is a ranked candidate list plus a propagation path plot: the disturbance's actual route through the plant, with the estimated lag labelled on every hop. That plot tends to be the thing people photograph and take into the meeting.

06

Evaluation & report

Four checks stand in for the test set you do not have:

  • Out-of-sample R². Does the fitted structure predict data it never saw?
  • Block bootstrap stability. How often does each link survive resampling?
  • Placebo injection. A synthetic cause with a known answer is injected. Does the method find it?
  • Method comparison. An agreement matrix across families.

Where ground truth is available, as with the synthetic demo, precision, recall, F1, and structural Hamming distance are reported directly. Everything exports as a self-contained HTML or PDF report, graph included.

★ Highlight feature

Domain knowledge as a first-class input

The feature I would defend hardest is the constraint editor, and it is the one that sounds least impressive on a feature list.

Every engineer looking at a plant already knows things no algorithm can infer from a few thousand samples. Flow goes this way. That valve cannot possibly affect the upstream tank. These four sensors sit on the same unit. That knowledge is usually better evidence than anything a statistical test will produce from a short record, and most causal discovery tools give you nowhere to put it.

Three constraint types can be set before discovery runs:

  • Forbidden links — ruling out directions that are physically impossible.
  • Required links — forcing couplings you know exist but the record may be too short to reveal.
  • Upstream tier ordering — assigning variables to process tiers so links may only flow forward.

They apply to every method, are stored with the graph, are honoured by the reliability tests, and are printed in the report. The effect is not cosmetic. In the bundled demo, differencing the data induces two spurious backward links, exactly the kind of artefact that makes a graph quietly wrong. A single tier assignment removes both, lifting precision from 0.71 to 1.00 and dropping structural Hamming distance from 2 to 0. One minute of process knowledge, entered once, outperformed every algorithmic refinement I tried.

The AI assistant

As in the FDI toolbox, an optional assistant dock is available from every page, and it knows the live state of your analysis: the variables loaded, the constraints you set, the graph just discovered, the monitoring flags, the current ranking. Its answers are about your run, not causal inference in general.

It works with OpenAI, Anthropic, a local Ollama model, or a custom internal endpoint, so it can run entirely on-premises when process data cannot leave the site. It interprets and suggests; it never edits your data or your settings.

One deliberate limitation: on the public demo the assistant is left unconfigured. The narrative summary in the report is written from the numbers by template, with no API key and no internet access required, so the tool is fully useful with the assistant switched off entirely.

Who it's for

In the field

Process & control engineers

You have the historian data and you have a theory about what happened. This gives you a way to test the theory rather than argue it, and a propagation diagram to put in front of people who were not in the control room. Constraints let you encode what you already know about the unit, so the tool works with your process knowledge instead of ignoring it. The report exports straight into an incident write-up.

Reliability

Reliability & maintenance teams

The costly mistake in root-cause work is replacing the loudest asset rather than the responsible one. Ranking by upstreamness and earliness rather than by deviation magnitude is aimed squarely at that: the sensor screaming hardest is frequently a victim, not a culprit. The structural monitor also flags degradation that never breaches an alarm limit, which is exactly the failure mode that shows up as a surprise.

Research & teaching

Researchers & students

Nineteen methods across four families sit behind one interface with one output format, which makes this a ready-made bench for comparing them. The synthetic process has known ground truth, so precision, recall, F1, and SHD are computed for real rather than estimated. The reliability suite (bootstrap stability, placebo injection, out-of-sample R²) is the same one you would have to write yourself for a paper. As a teaching aid it makes the correlation-versus-causation lesson concrete in about five minutes: run cross-correlation, run conditional Granger, look at the difference.

How it's built

Causal RCA is a single-page web application written entirely in Python on Dash. There is no separate JavaScript front end; the interface, the callbacks, and the numerical work live in one codebase.

The stack

  • Dash and Plotly — the interface and every interactive chart.
  • Dash Cytoscape and NetworkX — the causal graph: layout, rendering, and the path algorithms behind propagation and upstreamness.
  • pandas and NumPy — data handling and lag-matrix construction.
  • SciPy and statsmodels — the VAR fits, F-tests, and stationarity treatment.
  • scikit-learn — the traditional ML engines: forests, boosting, SVR, Lasso, and the permutation-importance machinery.
  • tigramite for PCMCI and lingam for VarLiNGAM.
  • PyTorch (CPU build) — the five deep-learning engines.
  • ReportLab — PDF export.

Application architecture

  • Manual page routing. A single dcc.Location drives a router callback rendering each of the six pages on demand, so it behaves like a multi-page tool while staying one process.
  • Shared state via browser stores. Raw data, processed data, constraints, the discovered graph, monitoring results, and the assistant conversation each live in a dcc.Store, so you can move between stages without losing work.
  • One graph object, many producers. Every one of the 19 methods returns the same structure: a weighted adjacency matrix with lags, plus optional uncertainty. Monitoring, root-cause scoring, reporting, and the assistant all consume that one object, which is why adding a twentieth method is a contained change rather than a rewrite.

Drawing a causal graph that is actually readable

More effort went into this than I expected. A causal graph from real process data is a directed graph with cycles, self-loops, and lag labels, and the default force layout renders it as a hairball.

The layout breaks cycles using the Eades, Lin and Smyth heuristic, assigns layers, and draws left to right so that upstream is genuinely to the left. Node styling matches the propagation plot exactly, with the same glow-halo nodes, white rings, solid arrowheads, and lag labels, so moving between the two views does not require relearning the notation. Uncertain links are dashed and dimmed rather than hidden, because an edge the data is unsure about is information, not noise.

Long-running work, done responsibly

Discovery on a wide dataset, and especially neural Granger training, takes real time. Those actions run as Dash background callbacks backed by a diskcache manager, which is what powers the live progress bar and the working Cancel button. The work happens off the request thread and can be interrupted cleanly.

Graceful degradation

Three dependencies are optional by design. Without torch the five deep-learning engines grey out with a note on how to enable them; without tigramite PCMCI does the same, and without lingam so does VarLiNGAM. The other fourteen methods run regardless. The app never crashes because something is missing, it just offers less.

Deployment

The app is deployed on Microsoft Azure App Service in the Canada Central region, and the interesting part of that story is the constraint.

It runs on the F1 free tier: 1 GB of RAM, one shared core. I fully expected to have to disable the deep-learning family to fit, and I was wrong. All 19 methods are live on the free tier. The deciding move was pulling PyTorch from the dedicated CPU wheel index rather than the default, which is roughly 200 MB instead of 2 GB of CUDA packages nobody was going to use on a machine with no GPU.

The rest of the configuration follows from two facts:

  1. Single instance, always. Background-callback state lives in a local diskcache, so horizontal scaling would split the job state across machines. This is why App Service was chosen over Container Apps, which autoscales by default. Gunicorn runs with --workers=1 for the same reason.
  2. Generous timeouts. --timeout=1200, because a neural Granger fit on a wide dataset genuinely takes that long on a shared core.

The cache directory is set through an environment variable, defaulting to system temp when the runtime reports an Azure environment, so the same code runs unchanged on a laptop and in the cloud.

The honest caveat: the deep-learning engines work on the free tier but they are slow, and a large dataset will test your patience. For serious neural work, run it locally on a machine with a GPU. The other fourteen methods are comfortable.

Documentation

The repository includes complete documentation so anyone can start at their own pace: a step-by-step tutorial video, a picture-led quick-start guide, and a comprehensive manual explaining every stage, method, parameter, and metric in plain language, with no background in causal inference assumed.

One detail I am quietly pleased with: every figure and every quoted number in the manual is generated programmatically from a miniature re-implementation of the pipeline. Nothing in it is an illustrative sketch. The 0.71 to 1.00 precision figure quoted earlier is computed, not asserted, which means the documentation and the software cannot drift apart as the tool changes.

What's next

  • Non-stationary regimes. Automatic segmentation with a graph estimated per regime, instead of one global structure asked to describe a process that changed halfway through.
  • Tighter FDI coupling. Taking the detection output from FDI Analytics directly as the fault window, so the two tools become one workflow rather than two.
  • Topology import. Reading constraints from P&ID or tag-hierarchy files instead of manual entry, since the constraint editor is the highest-value feature and currently the most tedious to fill in.
  • Alarm integration. Combining alarm sequences with the inferred graph to explain alarm floods, which is where root-cause questions get asked most urgently and answered worst.
  • Interventional analysis. Simulating what the process would do if a variable were held constant, using the fitted structure.
  • Execution speed. Parallelised discovery and incremental re-estimation for the sliding-window monitor.

The toolbox is free to use and I would genuinely value your feedback. If you try it, tell me what worked, what broke, and what you would want next. I am especially interested in whether the constraint editor matches how engineers actually think about their process, because that is the part I had to guess at most.
